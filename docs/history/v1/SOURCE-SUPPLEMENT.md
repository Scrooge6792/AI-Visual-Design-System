## V0.3 · Visual Asset Core

### 核心架构

系统采用 Agent-First 和 Local-First 设计，以 SQLite 为结构化数据核心，本地文件系统保存实际素材。

真实文件、数据库、知识文档、Prompt 配方分别管理，通过稳定 ID 建立关联。

系统资产不依附 Eagle、Hydrus 或其他素材管理软件，所有重要数据必须能够迁移。

原图需要复制到受管理的本地仓库，而不是只登记外部文件路径。原始文件不可变，使用 SHA-256 进行内容识别及完全重复检测。

同一素材支持多个标签、多个创作领域与多个来源。不同图片之间支持相似、衍生、系列等关系。

未来预留本地 WebUI，通过统一业务接口浏览与检索资源，但第一版不开发。

### 原始逻辑数据模型

V0.3 设计了以下实体：

`files`：物理文件、哈希、路径、格式和尺寸。

`assets`：视觉资产身份、标题、状态、修订号。

`asset_sources`：来源 URL、作者、版权及许可信息。

`tags`、`tag_aliases`、`asset_tags`：标准标签、别名及素材多对多关联。

`asset_relations`：图片之间的衍生、相似与系列关系。

`analysis_runs`：AI 分析结果、模型信息、使用的提示词版本及时间。

`change_proposals`：待审核的新增、修改、删除等正式变更。

`review_events`：审核与修正记录。

`operations`：持久化操作及中断恢复状态。

注意：V0.4 后续将 `tags` 体系升级为以 `concepts` 为中心的受控词表。最终数据库设计应采用修订后的模型，而不是原样重复建立两套标签实体。

### 审核基础原则

Agent 可以读取、分析、暂存、创建和修改提案，但不能擅自写入正式数据。

审核必须绑定具体的提案 ID、修订号、内容摘要及原图哈希。

批准后如果文件、标签或内容发生变化，原有批准失效。

新资源只有正式提交完成后，才进入默认搜索索引。

已存在的正式资产发生标签或描述修改时，也需要重新审核。

## V0.4 · 多领域标签与专业术语体系

### 设计思想

采用 Faceted Classification（分面分类）+ Controlled Vocabulary（受控词表）+ Knowledge Linking（知识关联）。

不采用“人物 / 风景 / 插画 / 海报”四选一的固定分类树。

因为人物是画面主体，插画是表现形式，海报是作品形式与用途；同一张图可能同时符合多个领域。

领域使用可重叠的动态视图，不要求复制资源。

### 通用分面

初步设计了十二个分面：

`work_type`：海报、角色设定板、概念图等作品形式。

`subject`：人物、建筑、动物、植物等主体。

`scene`：城市、卧室、山川、森林等场景。

`style`：日系商业插画、复古波普、极简主义等视觉风格。

`technique`：赛璐璐式上色、水彩晕染、半色调网点等表现技法。

`composition`：镜头视角、景别、构图布局。

`lighting`：逆光、侧光、散射光等。

`color`：色彩关系、饱和度、冷暖对比。

`material`：材质与纹理。

`pose_action`：姿势与动作。

`mood`：情绪与氛围。

`usage`：作为姿势、服装、光影、构图、背景等参考的用途。

不是所有素材都必须填写全部分面；由 AI 根据实际内容和需求判断。

### 专业术语数据模型

参考 W3C SKOS、Getty AAT、ISO 25964、IPTC 和 Danbooru 等成熟标准或方法论，但不把这些体系作为强制运行时依赖。

采用 `concepts`、`concept_terms`、`concept_relations`、`concept_mappings`、`asset_concepts`、`concept_revisions` 等逻辑实体。

概念有稳定 ID、首选名称、中文和英文名称、严格别名、定义、分面及修订记录。

支持 `broader`、`narrower`、`related` 等关系。不能把相关概念直接视为同义词。

例如“侧逆光”可以成为“逆光”的下位概念，但“轮廓光”与“逆光”不能随意视为等价。

专业概念可以关联独立的 Markdown 知识文章、参考图片与 Prompt 模块。

### AI 标签的三种性质

A. 可观察特征：图中确实存在的人物、服装、建筑、姿势等。

B. 视觉解释：风格、技法、电影感、氛围等专业或审美判断。

C. 创作参考用途：适合用来参考什么、复用什么。

这三种性质需要区分，不应混为一谈。

作者、实际地点、IP 归属、版权等事实需要外部证据，不能从画风猜测。

AI 可以提出新术语，但未经审核不得自动加入正式标准词典。

优先复用现有概念和别名，减少重复标签，不强制给每张图生成大量标签。

第一版采用小规模可信核心词表，随真实素材按需扩展，不导入完整 Getty AAT。

## V0.5 · Agent 交互与可信审批协议

### VARP

系统内部采用 Visual Asset Review Protocol（VARP）。

原则为 Agent-First、Review Before Commit、Trusted Approval、Auditable & Recoverable。

主要流程：

用户提供图片及收藏意图。

Agent 分析图片、检测重复、匹配标准标签，提出结构化入库草案。

用户可以通过自然语言要求修改草案。

Agent 更新草案版本。

独立本地 Reviewer 展示最终内容，由用户明确确认。

受控提交器校验批准记录、文件哈希、内容摘要和目标修订号，再写入正式仓库。

### Reviewer

已正式确认采用**独立本地审核器**。

自然语言沟通主要在 Agent 中进行，Reviewer 专门负责预览素材、查看最终标签和内容、集中审核及用户确认。

Agent 不得通过自行填入 `approved: true` 或伪造确认文本来获得写权限。

正式批准必须来自独立可信的人机交互组件，且绑定具体草案版本。

同一 macOS 用户身份下的两个普通进程并不天然构成强制权限隔离，因此 Phase 0 必须实际验证 Codex 沙盒、Reviewer 和正式 Vault 之间的写入边界。

如果无法可靠实现，不允许擅自降低安全要求，应报告技术障碍。

### 提案格式

采用 JSON，并使用 JSON Schema 校验。

提案包含 `proposal_id`、`revision`、`operation`、`source`、`changes`、`concept_ids`、`uncertainties` 等。

批准绑定 `proposal_id + revision + proposal_hash + file_hash + target_revision`。

可考虑参考 RFC 8785 JSON Canonicalization Scheme 生成稳定内容摘要。

### 状态模型

Asset、Proposal、Operation 是不同对象，不应该合并成一套状态。

Asset：`staged`、`active`、`archived`。

Proposal：`draft`、`in_review`、`approved`、`rejected`、`superseded`。

Operation：`pending`、`committing`、`committed`、`failed`。

后续增加了持久化的 Deferred Review（延后审核）机制，应该使用独立待审核队列状态管理。

### 后续新增的暂缓审核要求

审核器必须支持“稍后”和“后续全部稍后”。

“稍后”只暂缓当前素材。

“后续全部稍后”仅对当前导入批次剩余的未审核素材生效，不影响未来批次。

这两种操作只需要保存原图、文件指纹、批次、来源、导入时间等基本信息。

允许跳过 AI 分析，不进行正式分类，不进入正式检索。

如果已有分析草案，可以保留供日后继续，但未经审核的结论不能成为正式标签。

暂缓审核资料应长期保留，不自动过期或删除。

未来可通过 Agent 查询待审核批次，并继续审核。

### 工具权限

Agent 可以调用读取、检索、暂存、分析、创建草案、修改草案、查看草案和请求审核等操作。

Agent 不得直接拥有可信批准或无条件正式提交权限。

`approval.record` 和 `commit.execute` 仅由受信组件内部调用。

本地 CLI 优先，未来可适配 MCP。

### 批量审核

支持单项审核、批量审核和批次暂缓。

用户可以集中修正标签，批准部分资源，或要求重新分析。

批量批准也必须能追溯每一项素材的具体批准内容。

### 安全约束

不可信图片、文件名、网页内容和元数据都属于数据，而不是 Agent 指令。

需要防止提示词注入、恶意路径、文件覆盖、错误文件格式及越权操作。

不对外开放正式库的直接写权限。

## 后续修订中需要优先采用的决定

### V0.6 搜索

第一版使用 SQLite、FTS5、标准标签匹配、术语别名、上下级概念、关键词和全文搜索。

中文短词需要回退策略，不能完全依赖 FTS5 Trigram。

严格过滤、优先匹配、明确排除分别处理，不允许为了凑结果擅自放宽用户硬约束。

正式资产检索与待审核队列检索必须隔离。

**搜索结果默认不展示“为什么命中”之类的解释。** 用户主动询问原因时，才按需提供解释。

语义向量、以图搜图后置。

### V0.7.1 存储与备份取舍

统一仓库包含 SQLite、正式原图、待审核图片、Markdown 知识、JSON Prompt、必要元数据。

图片使用 SHA-256 内容寻址，原图不可变。

第一版可以使用 SQLite `DELETE` 日志模式与 `synchronous=FULL`，无需强制 WAL。未来 WebUI 有并发需要时再评估 WAL。

保留最小事务一致性、幂等提交、中断恢复、原始资料保护和可迁移性。

**取消复杂备份恢复、在线快照、自动备份、专门恢复程序、容灾系统等功能。**

用户会在停止数据库操作后，直接通过 macOS Finder 复制或压缩完整 Vault 文件夹，再保存到其他存储设备。

正式验收要求是：整个 Vault 文件夹复制到其他位置后，无需依赖原绝对路径即可重新使用。

### 成本、工具和第三方依赖

用户已有 SQLite、ChatGPT Plus 和 Codex Desktop。

默认零额外费用，不增加付费 AI API、云服务器或核心商业应用。

第三方生产依赖必须已有正式稳定版，不采用 Alpha/Beta/RC；要有持续维护、足够成熟的用户或社区基础。如有 GitHub 仓库，原则上需要较高 Stars（一般 ≥1000，核心优先 ≥3000），并检查安全、隐私及许可证。

不满足门槛的项目可以作为设计参考，但不能直接作为核心生产依赖。

需要优先查找已有成熟方案、Prompt 和方法论，解释价值与不足，再决定采用或自研。

AI Visual Prompt Cookbook 的结构化 Prompt 思路值得学习，但不能直接作为不可替代的核心依赖。

### 验收策略

用户自行完成主要的使用体验验收。

Codex 只需要进行必要的自动化检查和安全测试，不安排消耗大量模型额度的反复人工式验收。

出现 Bug、权限问题或用户明确要求时，再进行针对性复核。
