## 一、V0.5 审核协议补充：支持暂缓入库

我建议将暂缓操作设计成正式的 **Deferred Review（延后审核）** 机制，而不是简单地跳过确认。

**本地审核器 · 操作设计**

Agent 完成素材暂存后，提供以下操作

**批准入库**

正式归档、标签生效

**退回修改**

让 Agent 调整草案

**稍后**

仅当前素材暂缓

**后续全部稍后**

当前导入批次剩余素材暂缓

建议将“后续全部稍后”的作用范围限定为**当前导入批次尚未处理的素材**，不会永久关闭未来批次的审核，也不会批准任何资源。

两种暂缓操作都应遵循以下规则：

- 原始图片保存到受管理的待审核区，记录文件 ID、哈希、来源、导入时间和所属批次。
- 不强制进行 AI 分析，不分配正式分类标签；如果此前已有分析草案，可以保留供日后继续。
- 状态标记为 `deferred`，**不进入正式资产检索索引**，但允许通过专用待审核查询找回。
- 不因暂缓而自动过期、删除或批准；后续可以按批次恢复审核。
- 暂缓操作不消耗一次正式批准，后续仍须经过独立审核器。

例如，你一次收藏 30 张图片，只审核了前 5 张，点击“后续全部稍后”，剩余 25 张就进入待审核队列。之后只需告诉 Agent：“把上次没审核的图片找出来，继续处理。”

这给我们带来一个重要的数据设计调整：**待审核区也是持久化存储，但不是正式知识库。** 它可以记录基本文件信息，却不能把未经批准的 AI 判断当作正式检索事实。

## 二、现有检索方案调研

这次优先研究成熟、无需额外购买、能在本地运行的技术。结论是：**第一版不需要独立搜索服务器，SQLite 本身就能承担检索核心。**

| 技术 / 方法 | 现成能力 | 采用建议 |
|--------|--------|--------|
| urlSQLite FTS5https://www.sqlite.org/fts5.html | 全文索引、查询语法、BM25 相关性排序、Trigram 子串搜索 | 第一版核心 |
| urlSQLite Recursive CTEhttps://www.sqlite.org/lang_with.html | 查询多层级标签关系 | 第一版采用 |
| urlW3C SKOShttps://www.w3.org/TR/skos-reference/ | 术语同义、上下级、关联关系及层级展开 | 延续 V0.4 |
| urlcppjiebahttps://github.com/yanyiwu/cppjieba | 中文分词、自定义词典、正式版本持续更新 | 作为可选升级 |
| url信息检索评估方法https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-information-retrieval | Precision\@K、Recall\@K、MRR 等指标 | 用于验收 |

SQLite FTS5 已内置 BM25 排序、`unicode61` 分词和 `trigram` 分词等能力；SQLite 的递归查询也足以处理初期的专业术语层级。citeturn836489search0turn476169search6turn836489search2

cppjieba 已有 5.x 正式版本，最近的发布记录中包含测试和分词词典维护工作。它值得后续验证，但目前没必要引入 C++ 分词组件作为新的运行依赖。citeturn476169search4

有一个必须提前说明的技术问题：SQLite 默认的 `unicode61` 并不是专用中文分词器，而 `trigram` 的全文匹配通常需要至少三个 Unicode 字符。比如搜索“逆光”这种两个汉字，不能只依赖 Trigram 索引。citeturn836489search0

所以第一版我建议采用**标准术语精确匹配 + 中文子串查询 + FTS5 全文检索**的组合，先用实际素材衡量效果，再决定是否加入中文分词器。

此外，你已安装 SQLite，不代表 Codex 运行时连接的 SQLite 一定包含相同的 FTS5 编译能力。实施时需要做一次环境检测，但目前无需变更安装。

# 三、搜索方式：由 Agent 理解意图，由 Core 执行检索

我不建议 Agent 自行编写 SQL 查询数据库，也不希望它凭记忆猜测你收藏过哪些图片。

最理想的流程是：

**你的自然语言**

“找适合秋季人物海报的参考，要柔和侧光，不要太复杂的背景。”

**Agent Query Planner**

理解语义、查找标准标签、构造检索计划

**Search Engine**

条件过滤、标签扩展、全文匹配、排序

**Agent 返回素材**

缩略图、资源 ID、命中依据、适用价值

这里建议明确区分两种能力：

- **检索**：系统根据已批准的数据查找真实存在的资产。
- **推荐**：Agent 基于检索结果判断哪些素材更适合当前创作需求。

只有完成检索后，才允许 Agent 推荐具体资源，不能将自己推测的图片当作库中已有素材。

## 3.1 引入结构化 Search Query

延续之前结构化 Prompt 的设计思想，我建议自然语言搜索也转换成结构化 JSON。

例如：

```json

{
  "scope": "active",
  "must": [
    {
      "facet": "subject",
      "concept": "人物"
    }
  ],
  "should": [
    {
      "facet": "lighting",
      "concept": "柔和侧光"
    },
    {
      "facet": "usage",
      "concept": "海报参考"
    },
    {
      "text": "秋季穿搭"
    }
  ],
  "must_not": [
    {
      "concept": "复杂背景"
    }
  ],
  "limit": 10
}
```

以上是检索契约示例，概念名称在真正执行前必须通过词典解析成正式 `concept_id`；“复杂背景”如果不是词典中已有的概念，就应作为文本偏好或待解释条件处理，不能假装存在对应的标准标签。

搜索条件分为三类：

| 类型 | 含义 | 处理 |
|--------|--------|--------|
| `must` | 必须满足 | 严格过滤 |
| `should` | 优先匹配 | 影响排名 |
| `must_not` | 明确排除 | 在可验证条件下排除 |

对于“不太复杂”“有点温馨”“比较有电影感”这样的描述，Agent 可以先尝试匹配已有标准术语或文本描述。无法准确结构化时，应保留原始语义，而不是擅自生成一个未经审核的新标签。

另外需要提供 `scope`，明确本次搜索针对正式素材、待审核队列还是其他数据集合。

## 3.2 搜索条件不能被悄悄改变

假设你说：

“找没有人物的日系城市风景。”

如果搜索不到，Agent 不应该为了凑够结果，把包含人物的插画也当成完全匹配结果。

正确处理方式是先报告没有满足全部约束的结果，然后可选地提供放宽条件后的候选，并清楚说明哪些要求被放宽了。

这样能避免“找到了很多图，但根本不是我要的内容”。

# 四、第一版采用四种检索通道

**通道 A：标准标签检索**

直接匹配经审核的标准术语 ID，支持多标签 AND / OR、排除条件和分类维度。

例如：`侧逆光 + 雨夜 + 环境插画`。

这是第一版准确性最高的检索通道。

---

**通道 B：术语关系检索**

使用 V0.4 的概念词典，支持别名归一、上下级概念展开。

例如：搜索“逆光”时，可以包含已明确归属于逆光的下位概念。

但 SKOS 的 `related` 关系仅表示相关，不代表同义。因此默认不把相关术语自动加入严格匹配结果。citeturn836489search4

---

**通道 C：描述与全文检索**

搜索经审核的标题、内容描述、设计价值说明和其他正式文本字段。

例如：搜索“窗边散落的暖色阳光”，即使它不是一个标准标签，也可以找到描述中包含相关内容的图片。

初期使用 FTS5 加精确、短词与子串匹配回退机制。

---

**通道 D：结构化条件检索**

根据来源、时间、文件类型、画幅比例、尺寸、收藏批次等元数据过滤。

例如：找最近一个月保存的横版海报素材，排除低分辨率图片。

这部分不依赖 AI 语义分析。

将来要加入的视觉语义向量、以图搜图，只需要作为第五种检索通道接入，再与当前结果融合，不必推翻已建立的术语和全文搜索机制。

# 五、搜索结果应该如何排序？

找到包含关键词的图片，并不等于找到了有价值的参考。

例如你搜索“半色调网点海报”，下面两种图片都可能匹配：

- 图片 A：确实以半色调网点作为主要视觉形式。
- 图片 B：只是背景角落出现了一小块网点装饰。

显然，A 应该排在 B 前面。

我建议采用**规则优先、相关性排序辅助**的方案。

| 匹配类型 | 初始优先级 |
|--------|--------|
| 完全匹配标准概念 | 最高 |
| 匹配已确认的同义词 | 与标准概念等价 |
| 匹配明确的下位概念 | 高 |
| 匹配标题、主要设计价值 | 中高 |
| 匹配普通描述文本 | 中 |
| 仅有宽泛相关概念 | 默认不直接纳入结果 |

对于全文匹配，使用 SQLite FTS5 的 BM25 排序作为一个分数来源。FTS5 还支持按列设置不同权重，因此标题和设计价值说明可以比一般描述拥有更高权重。citeturn836489search0

不建议现在就把各类分数硬编码成一套复杂公式。第一版先建立简单、可解释的排序规则，再用真实查询进行调整。

## 5.1 搜索结果需要解释“为什么命中”

这是 Agent-First 模式非常有价值的一项能力。

示例：搜索「适合雨夜海报的城市背景」

**城市雨夜 · 街道反光**

**命中依据：** 标准标签与标题描述符合搜索条件。

此处使用示意图片和模拟资产 ID，并非真实图库搜索结果。

对于未来的推荐功能，Agent 还可以进一步说明它为什么认为这张图符合当前创作需求，但应将**数据库中的已确认事实**与**Agent 当次的设计建议**区分展示。

# 六、待审核素材如何检索？

这是你刚刚增加的“稍后”功能带来的新要求。

我建议把系统划分为两个逻辑搜索空间。

**正式资产库**

已审核、可用于创作参考和正式检索

**待审核队列**

已保存、未确认，不参与正式检索

待审核队列应提供独立检索能力，但只使用可靠的基础信息：

- 原始文件名、来源、导入时间。
- 所属导入批次与暂缓状态。
- 你主动提供的收藏备注。
- 文件类型、尺寸与指纹。

AI 已经分析过但尚未审核的标签，可以在待审核详情中查看，不过不会被视为正式事实。

例如：

“找出上周暂缓审核的所有图片。”

“继续审核昨天收藏的 20 张图。”

“把待审核队列中重复的图片列出来。”

Agent 应当能够处理这些请求，并恢复对应批次的工作进度。

为了支持这种流程，V0.3 数据模型需要补充 `import_batches` 和 `review_queue_items` 等记录，明确“后续全部稍后”影响的是哪一批、哪些资源，以及哪些资源尚未处理。

我建议第一版增加一项统计能力：**待审核数量、各批次数量、最早待审时间**。这些信息可以由 Agent 在你询问时汇报，不需要默认打扰你。

# 七、索引的维护方式

检索功能不能只考虑查询，还需要保证索引与正式库一致。

我建议建立一张派生的搜索文档表，包含资产 ID、已批准标题、描述、设计价值文本和必要的可搜索文本。

索引构建流程如下：

1. 资产正式入库，或已批准的元数据修订提交成功。
2. 在同一受控事务流程中更新权威记录与对应搜索数据。
3. FTS5 使用受管理的同步机制保持索引一致。
4. 系统提供重建、校验索引的维护命令。

SQLite 官方支持通过触发器维护 FTS5 外部内容索引，也支持在不一致时重建索引；但如果使用外部内容模式，必须确保内容表与全文索引持续同步。citeturn476169search0

对于我们而言，还有两个要求：

**第一，任何待审核分析结果都不能进入正式搜索文档。**

**第二，索引应当能够从已批准的权威数据完整重建。**

这样即使以后更换分词方式或搜索引擎，也不需要重新分析全部图片。

# 八、搜索质量如何验收？

为了避免出现“功能可以运行，但实际找不到东西”的情况，我建议在第一版实施时建立固定的检索测试集。

测试内容包括：

| 测试类型 | 示例 | 验证目标 |
|--------|--------|--------|
| 精确标签 | “半色调网点” | 正确找到对应资产 |
| 中英别名 | “Halftone” | 与中文标准术语等价 |
| 层级概念 | “逆光” | 能找到明确的下位概念 |
| 短中文词 | “雪景” | 两字查询正常工作 |
| 组合条件 | “雨夜 + 城市 + 海报” | 多条件正确合并 |
| 排除条件 | “风景，不要人物” | 不违反排除要求 |
| 跨领域 | “适合人物插画的建筑光影” | 不被单一领域限制 |
| 描述检索 | “窗边透进来的柔和日光” | 能匹配有对应描述的素材 |
| 无结果 | “不存在的特殊风格名称” | 不制造虚假的检索结果 |
| 状态隔离 | 搜索未审核素材的 AI 标签 | 不出现在正式结果 |

测试建议仍采用第一版的 100 张左右素材和 20 个预先确认的检索问题。

**第一版核心验收指标**

# ≥85%

Hit\@5：含目标资源的前五结果查询占比

# 0

未审核 AI 标签进入正式索引的次数

---

此外记录 Precision\@5、MRR 和无结果查询的误召回情况。

Hit\@5 适用于有明确目标素材的查询；MRR 衡量首个相关结果的位置，Precision\@5 衡量前五项结果中相关项的比例。指标定义参照成熟信息检索评估方法。citeturn836489search2

85% 是我们当前设定的初始目标，不代表搜索功能天然能够达到。只有实际测试能说明是否需要引入更复杂的中文分词、查询扩展或向量检索。

特别是“温暖而孤独的城市氛围”这种偏抽象的视觉需求，第一版可能主要依靠已审核的氛围标签和描述匹配；等到积累更多素材后，语义向量检索会有更明显的价值。

## 九、Agent 检索接口建议

为了让未来 WebUI 和不同 Agent 使用同一套检索能力，我建议将搜索工具契约控制在较少的几个操作上。

| 工具 | 职责 |
|--------|--------|
| `search.assets` | 检索已批准的正式素材 |
| `search.concepts` | 搜索术语、别名及概念关系 |
| `search.pending` | 查询暂缓及待审核素材 |
| `search.related` | 查询同系列、衍生及明确关联资产 |
| `search.explain` | 获取结果的命中依据 |
| `search.suggest` | 为输入内容建议标准查询条件 |

其中 `search.suggest` 只是生成查询建议，不得自动创建标准标签。

所有查询都经由 Core 的结构化校验器转换成参数化数据库查询，Agent 不直接拼接 SQL 或 FTS 查询表达式。特别是 FTS5 的 `MATCH` 有自己的查询语法，用户输入的标点、引号和特殊操作符需要正确处理。citeturn959758search1

未来 WebUI 也调用相同接口，不重新实现搜索逻辑。

# 十、本轮架构决策

| 决策项 | V0.6 建议 |
|--------|--------|
| 主要检索引擎 | SQLite + FTS5 |
| 中文搜索 | 标准术语匹配 + 短词回退 + 子串与全文查询 |
| 词典关系 | SKOS 风格的同义词与层级展开 |
| Agent 职责 | 自然语言理解、查询规划、结果解释 |
| Core 职责 | 条件执行、过滤、排序、权限隔离 |
| 排序 | 明确标签优先，全文相关性辅助 |
| 正式搜索范围 | 仅已批准且有效的资产 |
| 待审核搜索 | 独立队列、独立接口 |
| 索引管理 | 可重建的派生数据 |
| 视觉向量检索 | 后置，不阻塞 V1 |

## 二、文件仓库设计：物理存储与逻辑分类完全分离

我建议建立一个名为 `VisualAssetVault` 的本地仓库。

核心原则是：**实际文件按稳定标识管理，用户可理解的分类和标签放在数据库中。**

**VisualAssetVault/** [复制结构]

这里有三个值得提前确定的细节。

### 2.1 不按标签创建物理目录

不要采用：

`人物/秋季/毛衣/蓝色/`

这样的物理路径。

一张图片可以同时涉及人物、服饰、场景、插画和海报设计。如果通过文件夹分类，就会遇到重复存储、移动文件和目录管理的问题。

正式素材的路径由系统自动生成，例如：

`objects/sha256/ab/cd/<完整文件哈希>`

人类可读的名称、分类与标签则保存在 SQLite 中。

未来你通过 Agent 或 WebUI 查找图片，不需要知道文件实际位于哪个目录。

### 2.2 原始图片不应被修改

导入之后，原始图片采用不可变（Immutable）管理策略。

即使以后你修改了图片的标题、标签、描述或分类，也不能直接重写原文件。

如果对图片进行裁剪、改色、局部修图或生成新版本，创建新的素材文件，并建立衍生关系。

这样可以保护你最早收藏的素材，也便于以后重新分析。

### 2.3 暂缓审核的资源同样持久保存

根据你确定的“稍后”“后续全部稍后”功能，`staging/deferred/` 不属于临时缓存。

其中的图片可以长期保留，直到你主动审核或决定删除。

系统不会因为尚未分类而自动清理它们。

待审核资源仍应具有稳定 ID、文件哈希、导入批次、来源与状态，但不会进入正式视觉标签和检索索引。

## 三、SQLite 存储策略

### 3.1 建议采用 WAL + FULL 同步策略

SQLite 的 WAL（Write-Ahead Logging）模式允许读取与写入并发，适合未来 Agent 和 WebUI 同时访问资产库的场景。citeturn472187view1

建议初始配置如下：

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

其中：

- `WAL`：改善读写并发。
- `synchronous = FULL`：优先保障已提交事务在断电情况下的持久性，而不是追求最高写入速度。
- `foreign_keys = ON`：启用资产、标签、分析记录等实体的外键约束。
- `busy_timeout`：避免短暂的数据库写入竞争直接失败。

SQLite 官方说明，在 WAL 模式下，`FULL` 会在每次提交时增加同步操作，以增强断电后的事务持久性。citeturn897388search13

这些设置将在 Codex 实施时通过性能与异常测试验证，而不是直接假定所有 SQLite 构建具有一致的行为。

**发现一项需要优先检查的 SQLite 版本问题**

SQLite 官方在 2026 年 3 月修复了一个罕见的 WAL-reset 数据库损坏问题。该问题影响 3.7.0 至 3.51.2 的部分并发使用场景，已在 3.51.3 及部分回移补丁版本中修复。citeturn783857search0

因为你的本机已经安装 SQLite，实施时应首先检查：

- 命令行 `sqlite3` 的版本。
- 实际程序链接的 SQLite 版本。
- 是否包含相关安全修复。
- 是否支持 FTS5 和所需编译选项。

如果检测到未修复的版本，应先升级或选择受支持的数据库运行环境，而不是在有并发写入风险的情况下直接开启 WAL。

### 3.2 不允许多个组件随意写数据库

我建议建立一个统一的数据库写入协调器。

虽然 SQLite 可以处理并发连接，但我们还需要处理文件复制、审批状态、搜索索引、操作日志等多个步骤。

所以第一版应保证：

- Agent 不直接执行正式数据库写操作。
- 所有正式修改由 Visual Asset Core 执行。
- 每次写入具有唯一操作 ID，支持重复请求幂等处理。
- 查询使用独立的只读访问接口。
- 未来 WebUI 使用同一业务接口，不直接修改数据库。

这不是为了规避 SQLite 的并发能力，而是为了保证**一项业务操作从开始到结束具有统一的状态和恢复规则**。

## 四、文件与数据库的一致性

这里存在一个实际问题：

SQLite 能保证数据库内部的事务完整性，但不能把文件系统操作和数据库操作合并为一个原子事务。

比如，图片已经成功复制，但程序在写入 SQLite 之前崩溃，就可能产生孤立文件。

SQLite 官方的原子提交保证针对数据库事务本身，并不涵盖我们的外部图片文件。citeturn472187view2

因此，我建议采用**持久化操作日志 + 可恢复的提交状态机**。

### 4.1 正式入库流程

**01 · 校验已批准的提案**

版本、内容摘要、文件哈希、审批记录

**02 · 记录待提交操作**

生成唯一操作 ID，保存恢复所需信息

**03 · 确保持久文件已就绪**

校验原图，移动或复用内容寻址对象

**04 · SQLite 事务提交**

资产、标签、审核记录、正式状态、检索文档

**05 · 完成并清理**

返回结果、清理冗余暂存文件、保留操作历史

其中有两条重要约束：

**第一，正式资产只有在数据库事务完成、且对应文件已验证可用时才对检索可见。**

**第二，操作失败不能立即盲目删除图片。**

因为同一文件可能已经被其他资源引用，或者属于一个尚未恢复完毕的提交操作。

恢复机制需要根据操作日志、文件指纹和引用关系判断应该继续、回滚还是保留待处理。

### 4.2 异常场景如何处理

| 异常 | 系统行为 |
|--------|--------|
| 文件复制中断 | 保留待恢复记录，重新校验并复制 |
| 图片已就绪，数据库未提交 | 重试提交或安全回收未引用对象 |
| 数据库已提交，程序未返回结果 | 根据操作 ID 返回已有结果，不重复入库 |
| 图片哈希与审批记录不一致 | 停止提交，要求重新审核 |
| 磁盘空间不足 | 停止当前操作，保留已完整暂存的素材 |
| 数据库被其他程序占用 | 有限重试，仍失败则报告 |
| 搜索索引损坏 | 从已批准数据重新构建 |
| 原始图片丢失 | 标记资产异常，从备份恢复，不伪造成功结果 |

文件写入还需要正确处理磁盘同步、同卷移动和崩溃恢复。不能仅凭一次文件重命名，就认定整个文件与数据库组合操作已经具有原子性。

## 五、暂缓审核资源的生命周期

这是 V0.7 相较于之前方案的重要补充。

既然你可以选择“稍后”或“后续全部稍后”，系统必须把未审核资源当作需要长期保护的资料，而不是随时可以删除的缓存。

建议明确下面的生命周期：

**Staged · 已暂存**

**Deferred · 稍后**

保持待审核，可长期保存

**In Review · 审核中**

分析、修改与确认草案

**Committed**

正式入库

**Rejected**

拒绝归档

“拒绝归档”与“删除原图”是不同操作。

我建议默认拒绝仅关闭入库提案，原始暂存文件进入待清理状态。真正删除仍由独立操作决定，避免误点导致收藏素材永久丢失。

同时，待审核素材需要进入备份范围。否则你保存了几百张图并选择稍后处理，一次磁盘故障就可能让所有未审核素材消失。

### 不建议采用的做法

不建议给待审核资源设置固定的 7 天、30 天自动删除期限。

更合适的是由 Agent 在你主动要求整理时报告数量和占用空间；只有你确认之后才清理可删除内容。

## 六、安全设计：关键是保护真实数据和审批边界

我建议将安全问题分为四类处理。

### 6.1 文件安全

网络收藏的图片属于不可信输入。除了图片自身可能包含恶意文本之外，文件解析器也可能存在安全漏洞。

OWASP 的文件上传安全规范明确建议采用格式白名单、内容类型校验、文件大小限制、安全文件命名和隔离存储等措施。citeturn783857view0

第一版建议：

| 措施 | 具体要求 |
|--------|--------|
| 文件类型白名单 | 仅允许明确支持的图片格式 |
| 真实格式校验 | 不仅检查扩展名，还要验证文件内容 |
| 资源限制 | 限制单文件体积、解码后的像素数及批次大小 |
| 安全命名 | 受管理文件名由系统生成 |
| 路径保护 | 阻止路径穿越、符号链接逃逸及任意文件覆盖 |
| 原图不可变 | 不对已保存原图执行覆盖修改 |
| 解析隔离 | 对可疑或不支持的文件停止解析 |
| 安全预览 | WebUI 使用受控缩略图，不执行图片内的主动内容 |

GIF、WebP、HEIC、AVIF 等格式后续需要根据实际使用频率和原生解码支持进行验证。

对于暂时不能安全解析的格式，可以保留文件并提示处理状态，但不能假装已经成功完成视觉分析。

### 6.2 Agent 权限隔离

这是整个系统最重要的安全边界。

我们之前已经确定使用独立本地审核器，因此建议形成三个不同的执行角色：

Agent

分析与创建提案

Reviewer

接收用户确认

Core

执行正式写入

建议在 macOS 上重点验证 **App Sandbox + 独立审核进程 + 受控本地通信** 的实现路线。

Apple 官方文档说明，App Sandbox 能限制应用对文件系统的访问；macOS 14 以后还会根据代码签名识别沙盒容器所属应用，并处理其他应用尝试访问容器的情况。citeturn459620search3

但必须明确：**独立进程不天然等于权限隔离。**

如果 Codex 能直接读写审核器的数据库文件或调用其内部审批操作，那么独立窗口也无法保证审批安全。

因此后续实施时，必须实际验证 Agent 无法绕开 Reviewer 修改正式资产，不能仅凭程序结构认为安全已经成立。

如果第一版无法达到这个要求，应该先完成沙盒与受信写入的技术验证，而不是降低已有的审批约束。

### 6.3 网络和隐私

虽然这是 Local-First 系统，但你的主要图片分析工具是 GPT。

所以要区分两个概念：

- **资产本地存储**：图片和数据库长期保存在你的 Mac。
- **图片分析位置**：通过 GPT 分析时，相关图片会提交给相应的模型服务。

Local-First 不代表所有 AI 分析完全离线。

我建议系统明确标记分析执行位置，并遵循以下策略：

- 不自行将整个素材库上传到云端。
- 一次分析只提供完成任务所需的图片和上下文。
- 不在日志中记录模型密钥、访问令牌或隐私性 URL 参数。
- 将图片 EXIF 等元数据视为可能包含隐私信息的数据。
- 原图保留原始元数据；对外分享或导出时支持生成去除敏感元数据的副本。
- 本地 WebUI 将来默认仅监听 `127.0.0.1`，并实施访问控制，而不是默认向局域网开放。

如果未来接入第三方视觉模型或新的 AI API，再逐项评估上传行为、数据保留政策和费用。

### 6.4 第三方依赖安全

延续之前确认的准入规则：

正式版、持续维护、GitHub Star 数达到约定门槛、免费优先，并检查安全和隐私。

本轮暂时不引入新的运行时第三方应用。

SQLite、Apple 原生框架与成熟开放安全规范已经能够提供主要基础能力。

# 七、备份与恢复：必须同时保护图片和数据库

只备份 SQLite 不够，因为真正的图片都在文件系统中。

反过来，只复制图片也不够，因为你多年积累的标签、分析记录、来源、审核历史都保存在数据库中。

因此，**一次有效备份必须同时包含数据库与它引用的文件，并保证两者对应同一个一致的状态。**

## 7.1 建议采用三层保护

**第一层：日常完整性检查**

检查数据库结构、外键关系、文件是否存在、文件哈希及索引一致性。

SQLite 官方的 `integrity_check` 不包含外键约束检查，需要配合 `foreign_key_check` 使用。citeturn459620search1

无须建立额外备份副本，主要负责发现问题。

---

**第二层：Visual Asset Vault 快照**

由 Core 统一创建可恢复备份，包含一致的 SQLite 快照、原图、待审核资源、知识文档、Prompt 以及校验清单。

对数据库使用 SQLite Online Backup API，避免直接复制运行中的数据库文件。citeturn472187view0

第一版必须实现备份与恢复命令。

---

**第三层：独立存储介质备份**

使用 macOS 自带的 Time Machine，或者将经过校验的 Vault 备份复制到已有的独立存储设备。

Apple 支持使用外置存储设备进行 Time Machine 备份，也提供备份加密选项。citeturn897388search0turn897388search8

不必购买付费备份软件，但真正的硬盘故障保护仍需要独立备份位置。

尤其要注意，**同一块磁盘上的另一份备份不是完整的灾难恢复保障**。

它能帮助修复误操作，但不能保护整个磁盘损坏的情况。

在你暂时不考虑额外硬件投入的前提下，第一版可以先提供正确的备份、导出和恢复机制。如果已经有可用的外置存储设备，再配置独立备份。

## 7.2 Vault 快照如何确保一致性？

建议第一版采用简单、可靠的方式：

1. Core 暂停新的正式写入，等待正在执行的提交完成。
2. 创建 SQLite 的一致性快照。
3. 根据该快照收集正式资产、待审核资产及知识文件。
4. 生成包含文件哈希、数据库版本与快照标识的清单。
5. 校验备份内容，完成后恢复正常写入。

为简化第一版的实现，短暂暂停写入比提前开发复杂的在线增量快照机制更合适。

未来如果图片数量很大，再加入增量备份与内容去重。

## 7.3 恢复不仅是重新复制文件

恢复流程应检查：

- 备份格式和数据库 Schema 版本是否兼容。
- 文件数量、大小和哈希是否匹配。
- 正式资产是否能定位到原图。
- 未审核资源是否完整恢复。
- 标签、来源、审核记录和知识文件是否一致。
- 全文索引是否能够重新构建。

恢复过程必须先生成报告，避免直接覆盖现有资源库。

我建议默认执行**恢复到新位置并验证**，验证成功后再由你决定是否替换当前仓库。

## 八、哪些内容可以自动清理？

为了长期使用，最好现在就明确哪些数据属于可再生资源。

| 类型 | 自动清理策略 |
|--------|--------|
| 正式原图 | 不允许自动删除 |
| 暂缓审核原图 | 不允许自动删除 |
| 已批准的分析与标签 | 不允许自动删除 |
| 知识文档、Prompt 配方 | 不允许自动删除 |
| 缩略图、临时预览 | 可自动重建与清理 |
| 全文及向量索引 | 可重建，但不得丢失权威数据 |
| 未引用的中间文件 | 经确认无恢复需求后可清理 |
| 历史审核记录 | 保留，不随普通缓存清理 |
| 旧备份 | 根据保留策略清理，避免删除唯一有效备份 |

这套规则可以概括为：

**原始资产和人工审核成果是长期数据；缓存与检索索引是派生数据。**

这也符合你之前强调的，系统真正重要的是多年积累下来的知识与素材，而不是某个软件或索引引擎。

# 九、本轮验收标准

建议将存储、安全和恢复单独设为一个验收模块，避免只测试“正常导入一张图片”。

| 测试场景 | 必须达到的结果 |
|--------|--------|
| 正式入库中途强制退出 | 能恢复或安全终止，不出现虚假的成功记录 |
| 同一图片重复导入 | 不重复保存相同内容，来源信息可保留 |
| 已审核图片被篡改 | 哈希校验发现异常 |
| Agent 直接修改 Vault | 被权限边界阻止 |
| Agent 伪造审批记录 | 无法提交正式变更 |
| “后续全部稍后”后重启 | 待审核队列和批次状态完整 |
| 数据库意外损坏 | 能从有效备份恢复 |
| 删除缩略图与搜索索引 | 能完整重建 |
| 恢复到另一目录 | 资源仍可正常检索 |
| 存储空间不足 | 不产生不完整的正式资产 |
| 不可信图片或路径输入 | 不发生任意文件写入或执行 |
| 备份完成后校验 | 数据库、文件和清单一致 |

建议把这些测试自动化，尤其是故障注入、审批绕过和备份恢复。

此外，需要在模拟环境验证权限隔离，不直接用已有的重要素材做破坏性测试。

## 三、SQLite 第一版不必强制使用 WAL

之前采用 WAL 主要是考虑 Agent 与未来 WebUI 的并发访问。

但第一版实际上是单用户、低频写入，所有正式操作都经过 Core，WebUI 也暂不开发。

因此可以先采用 SQLite 默认的 `DELETE` 日志模式。

```sql
PRAGMA journal_mode = DELETE;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

它具备正常的事务提交与回滚能力。在事务顺利结束、数据库连接关闭后，通常只需要保存主数据库文件。SQLite 官方也明确指出，`DELETE` 是默认日志模式，事务完成时回滚日志会被删除。citeturn714074search2

这给我们带来两个好处：Finder 备份更直观；第一版也不必处理 WAL 检查点与额外日志文件的管理细节。

未来 WebUI 真正需要并发读写时，再评估切换到 WAL。这个调整不影响核心数据模型。

## 四、但有三项可靠性措施不建议删除

我建议区分**备份容灾**和**正常业务可靠性**。

**数据库事务与文件一致性**

防止 Agent 入库途中崩溃后留下错误的正式资产记录。保留最小操作日志、幂等提交和未完成操作恢复。

**原始素材保护**

原图不可变，暂缓审核图片持久保存，未经批准不得修改正式标签和知识。

**仓库可迁移性**

所有必要数据集中在同一目录，内部使用相对路径或稳定资产 ID，不依赖当前 Mac 上的绝对路径。

其中第三项是关键。

我们应把“**复制整个文件夹，在另一位置解压后仍能直接打开**”设为第一版的正式验收条件。

这比开发一套复杂备份系统更符合你的需求，也能从架构上避免被特定软件绑定。
